<objective>
Give the front desk one board with every room's housekeeping status and its derived occupancy for a business date (ROOMS-01, D-02, D-11, D-12, D-13). After this plan, `GET /front-desk/room-board` answers in four queries however many rooms exist.

</objective>

## Flagged Assumptions

- **FA-02-1.** Occupancy is night-based as D-02 is written: on its check-out day a still-checked-in guest's room reads `vacant` with `departing_today: true`. The docs in 02-04 say so explicitly, and Phase 3's check-out verb changes the reservation status.
- **FA-02-2.** `arriving_today` follows D-02's wording (any reservation that is neither cancelled nor checked_out). A pending_verification hold that has expired but has not yet been released by `ReleaseExpiredHoldsAction` therefore still shows as an arrival.
- **FA-02-3.** A null floor sorts first. The decisions do not say where null floors go; both SQLite and MySQL put NULL first in ascending order, so the ordering is identical in tests and production.
- **FA-02-4.** `status_changed_by` is null both for rooms never moved through the endpoint and for rooms whose changer was deleted (`nullOnDelete`). Claude's Discretion allows null.
- **FA-02-5.** An unknown `room_type` uuid returns an empty list with 200 rather than 422, keeping the filter free of an extra query. A filter matching nothing is not a validation error.

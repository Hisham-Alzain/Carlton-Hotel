<objective>
Give the desk one check-in verb (RESV-03; D-01, D-02, D-05, D-13, D-14). After this plan, `POST /cms/reservations/{reservation}/check-in` resolves the room (given, pre-assigned or auto-picked), sets `checked_in`, stamps `checked_in_at`, enforces the hotel-local stay window with the day-before override, refuses maintenance rooms, and pushes the guest's "room ready" notification, all without touching the room's housekeeping status.

Purpose: check-in becomes an explicit, audited, locked transition instead of a side effect of `assign-room`; plan 03-04 then narrows `assign-room`.
Output: `CheckInReservationAction`, `CheckInReservationRequest`, `RoomOutOfOrderException`, `ReservationOutsideStayWindowException`, `GuestCheckedIn`, the union-typed listener, controller/service/route, three lang keys in five locales, `CheckInTest`, `CheckInReservationActionTest`.
</objective>

## Flagged Assumptions

- **FA-03-1.** When no room is given, none is pre-assigned and the picker finds none, check-in answers 409 `no_availability` (the existing booking code). D-01 names no code for this case.
- **FA-03-2.** `early_check_in: true` sent while today is already inside the window is ignored: no override is logged. `reason` is still validated whenever the flag is true.
- **FA-03-3.** Check-in (and plan 03-04's assign-room) also locks the room type row, the serialization point `CreateReservationAction` already uses, so two desks cannot hand one room to two reservations at once. D-01 names only the reservation lock; the extra lock follows the existing booking pattern. Lock order is always reservation, then room type.
- **FA-03-4.** Order of checks: status, stay window, room line, room resolution, room type, maintenance, overlap. A cancelled reservation outside its window therefore reports `reservation_state`.
- **FA-03-5.** A room of another type keeps answering 422 `reservation_state`, and a room another stay holds keeps answering 409 `room_already_assigned`, exactly as `assign-room` does today.
- **FA-03-6.** `GuestCheckedIn` is dispatched manually after `DB::transaction()` returns (the `RoomAssigned` style research recommends); `ReservationCheckedOut` (plan 03-05) uses `ShouldDispatchAfterCommit` because it can run inside the guest-approve transaction.

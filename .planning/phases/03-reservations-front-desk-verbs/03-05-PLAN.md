<objective>
Give the desk one check-out verb against a settled folio (RESV-04; D-06, D-07, D-08 room-status half, D-09, D-13, D-14). After this plan, `POST /cms/reservations/{reservation}/check-out` refuses an open folio with 422 `folio_unsettled` unless a `folios.settle` holder forces it with a logged reason, stamps `checked_out_at`, moves every assigned room to dirty through the Phase 2 single writer, and emits `ReservationCheckedOut` after commit.

Purpose: departure becomes a locked, audited transition with the money gate enforced in one place; plan 03-06 then routes the guest's express checkout through the same action.
Output: `CheckOutReservationAction`, `CheckOutMode`, `FolioUnsettledException`, `ReservationCheckedOut`, `CheckOutReservationRequest`, nullable actor on `UpdateRoomStatusAction`, the `GenerateFolioAction` guard, the resource `folio` summary, controller/service/route, two lang keys in five locales, and the tests.
</objective>

## Flagged Assumptions

- **FA-05-1.** `can_force` in the 422 context is computed from the calling user's `folios.settle` (super admins included through `Gate::before`), so the dashboard knows whether to offer the override.
- **FA-05-2.** D-07 is applied literally: `force: true` without `folios.settle` is 403 even when the folio is already settled. With `folios.settle`, force on a settled folio is an ordinary check-out, reported to listeners as mode NONE.
- **FA-05-3.** The `GenerateFolioAction` guard returns an existing folio unchanged once the reservation is checked_out, but still builds a folio it creates in that call (legacy checked-out stays with no folio), so it never returns an empty folio.
- **FA-05-4.** Rooms move to dirty with a null (system) actor for staff check-outs too, as the ROADMAP says ("system actor"); the staff user is on the reservation's own activity row instead.
- **FA-05-5.** For an open folio, check-out refreshes the line items once inside the lock before the gate (D-06 "create/refresh ... if missing/open"), so the 422 context and the forced-log total reflect current charges.
- **FA-05-6.** `ReservationCheckedOut` is dispatched from inside the transaction closure and relies on `ShouldDispatchAfterCommit`; this is the first use of the interface in the repo, proven by `test_event_is_dispatched_after_commit`.
- **FA-05-7.** The `folio_unsettled` refusal is raised after the transaction commits, not inside it. Throwing inside would roll back the folio that D-06 generates under the lock, so the 422's `folio_uuid` would name a folio that does not exist and the desk could not settle it. Nothing but the folio's creation or refresh is committed on that path.

<objective>
Close the key lifecycle and prove it cannot leak (GUEST-05 revocation and leakage; D-11, D-14). After this plan, check-out, cancellation (guest or staff) and time each end the key, the cancellation and its revocation are atomic, and one consolidated test enumerates every place the code could escape.

Purpose: a former guest must never retain a working code, and later phases must not be able to regress the exposure rules silently (CONTEXT "Specific Ideas").
Output: `RevokeDigitalKeyOnCheckOut`, the restructured `CancelReservationAction`, `RevokeExpiredDigitalKeysAction`, `ExpireDigitalKeys` (`stays:expire-digital-keys`) on a 15-minute schedule, `DigitalKeyLifecycleTest`, `DigitalKeyLeakageTest`.
</objective>

## Flagged Assumptions

- **FA-4.06-1.** The sweep runs every fifteen minutes (RESEARCH recommendation; D-11 fixes no cadence). Expired keys are already hidden at read time, so the cadence only bounds how long an expired ciphertext stays in the row.
- **FA-4.06-2.** The check-out listener is synchronous so the key dies with the check-out response even when no queue worker runs; it executes after the check-out transaction commits (the event is after-commit), so a revoke failure surfaces as an error without undoing the check-out, and the sweep (reason expired, at check-out time) is the backstop.
- **FA-4.06-3.** "Postman env refresh output" (D-11) is verified statically: the committed environment file and collection hold no key variable or code-shaped value, and the refresh command never reads a key column. Running the command inside a test would overwrite a tracked file.
- **FA-4.06-4.** The staff profile (`GET /guests/{guest}`, plan 04-08) asserts its own no-code rule; the leakage matrix here covers the staff routes that exist at this point.

# Phase 5 — Folio Extensions: Consultant Decisions

Inspected read-only: `Folio`/`FolioItem`/`Payment`/`Refund` models + migrations, `FolioStatus`, `PaymentMethod`, `GenerateFolioAction`, `SettleFolioAction`, `ApproveFolioAction`, `CheckOutReservationAction`, `RecordCashPaymentAction`, `ManualDriver`, `FolioService`, `PaymentService`, `ReceiptService`, both `FolioController`s, `PaymentController`, folio resources/requests, `routes/api.php`, `RolesAndPermissionsSeeder`, `EnsureIsCheckedIn`, `GuestEntitlement`, `StayController` (guest ownership precedent), `DomainException` + `bootstrap/app.php` envelope, `phpunit.xml` (sqlite :memory:), existing `FolioTest`/`PaymentTest`/`ConcurrencyTest`, tree node, both guides, PITFALLS §2/§9/§10, ARCHITECTURE folio rows, SKILL.md.

Facts that shape the decisions:
- `folio_items` today: `description` (plain string), `amount_usd` DECIMAL(10,2), `source_type` string (`reservation|service_booking|service_request`), `source_id` nullable, no actor, no quantity. `payments` today: morph `payable`, `method`, `amount_usd`, `recorded_by`, `note`, `status`; no reference/idempotency column. `refunds` table already exists (unused by routes).
- `GenerateFolioAction` **deletes every item and re-inserts** on each open-folio call (guest `GET /folio`, admin generate, every check-out). Left as is, any manual row would vanish and any dispute would dangle. This is the single most important change in the phase.
- Balance today lives only in `ReceiptService`: `total_usd − Σ completed payments`, where payments are collected against **both** the folio and the reservation (`POST /cms/reservations/{r}/settle` writes reservation-level payments).
- Lock order in Phase 3: reservation → folio. Tests run on sqlite (`lockForUpdate` is a no-op there); P8/P3 "race" tests are sequential state-guard tests.
- Guest precedent (Phase 4 `StayController`): someone else's record is **404 `not_found`**, never 403.
- Only `reception` holds `folios.view`/`folios.settle` today.

## Decisions

### FOLIO-01 — Folio read

- **D-01 (route, no auto-generate):** `GET /cms/reservations/{reservation}/folio` inside the existing `cms/reservations` group under a new `Route::middleware('permission:folios.view')` sub-group; controller `AdminFolioController::showForReservation(Reservation)`; `FolioService::adminShow(Reservation)`. Pure read, any reservation/folio status. No folio → new `FolioMissingException` (`folio_missing`, **404**, context `{reservation_uuid, reservation_status}`); the dashboard then calls the existing `POST /cms/folios/{reservation}/generate`. Rationale: requirement fixes 404; a GET that writes would break "receipt never regenerates" and the settled/checked-out guards. `stakes: low`, `convene: false`.
- **D-02 (one resource, additive):** No `FolioDetailResource`. `FolioResource` gains, all `whenLoaded`-guarded: `payments` (`PaymentResource::collection`), `paid_usd`, `balance_due_usd` (strings, 2dp, computed from the loaded `payments` relation, no query in `toArray`), `open_disputes_count` (computed from loaded `items.disputes`). `FolioItemResource` gains `quantity`, `unit_price_usd`, `posted_by` (`{uuid, name}` when loaded, null for generated rows), `posted_at`, `reason`, `reverses_item_uuid`, `dispute` (`{uuid, status, reason, raised_by: guest|staff, raised_at, resolved_at, resolution_note} | null` = latest dispute). Guest `GET /folio` therefore shows dispute status per item for free (PITFALLS UX row). Rationale: one shape for read, post, payment, settle and guest view; no client has to branch on endpoint. `stakes: medium`, `convene: false`.
- **D-03 (balance semantics):** `balance_due_usd = total_usd − Σ amount_usd of payments with status completed whose payable is this folio OR its reservation` (the reservation-level `settle` deposits count; otherwise a guest who paid on arrival would show a balance). Implement once as `Folio::ledgerPayments(): Builder` (moved out of `ReceiptService::paymentsFor`, which now calls it) and `Folio::paidUsd()/balanceDueUsd()` helpers that operate on the loaded collection. The service does `$folio->load(['items.disputes','items.poster'])`, `$folio->setRelation('payments', $folio->ledgerPayments()->with('recorder')->get())`, then hands the model to the resource. Refunds are not subtracted this phase (no refund route exists). Query bound: `expectsDatabaseQueryCount(≤ 6)` on the read path. `stakes: medium`, `convene: true` (money semantics shared with receipt and the check-out gate).

### FOLIO-02 — Manual line items

- **D-04 (schema, additive migration on `folio_items`):** `quantity` `unsignedSmallInteger default 1`; `unit_price_usd` `decimal(10,2) nullable` (null on generated rows); `posted_by` `foreignId nullable constrained users nullOnDelete`; `reason` `string(255) nullable`; `reverses_item_id` `foreignId nullable constrained folio_items nullOnDelete` (self-ref, credit → charge it reverses); `idempotency_key` `string(64) nullable`; unique `(folio_id, idempotency_key)`; unique `(folio_id, source_type, source_id)` (backs D-06 reconciliation; existing rows are distinct per source). `source_type` stays a string column but gets an enum `FolioItemSource { RESERVATION, SERVICE_BOOKING, SERVICE_REQUEST, MANUAL, ADJUSTMENT }`. `amount_usd` remains the **signed** line total: `manual` rows are `> 0`, `adjustment` rows are `< 0`. `description` stays a plain string (existing column; receipt already flags localisation as future). No `category`, no `voided_at`, no `tax`: `subtotal_usd == total_usd` until a tax rule exists. `stakes: high`, `convene: true`.
- **D-05 (endpoint):** `POST /cms/folios/{folio}/line-items`, permission **`folios.post`** (new, seeded in the `folios` group; every preset that holds `folios.settle` — today only `reception` — also gets `folios.post`). `PostFolioItemRequest` body: `{ kind: "charge"|"credit" (default charge), description: required|string|max:255, quantity: integer|min:1|max:999 (default 1), unit_price_usd: required|numeric|min:0.01|max:99999.99, reason: string|max:255 (required_if kind=credit), reverses_item_uuid: uuid|nullable (credit only; must belong to the same folio else 422 validation_failed) }`; optional header `Idempotency-Key` (D-08). `PostFolioItemAction::handle(Folio, User $poster, array $data)`: `DB::transaction`; `Folio::whereKey()->lockForUpdate()`; status must be `open` else new `FolioSettledException` (`folio_settled`, 422, context `{folio_uuid, settled_at}`); reservation status is **not** a guard (late charges after a forced check-out are the point); `amount = ±quantity × unit_price` computed with `bcmul`/2dp; a credit that would take `total_usd` below zero → new `FolioCreditExceedsTotalException` (`folio_credit_exceeds_total`, 422, context `{total_usd, amount_usd}`); insert row (`source_type` manual|adjustment, `source_id` null, `posted_by`); `Folio::recalculateTotals()` (D-07); respond **201** with the full `FolioResource` (D-02). No PATCH/DELETE for items ever: corrections are `credit` rows. Rationale: one endpoint for charges and credits keeps the ledger append-only and gives the desk the "reverse a charge" verb without an edit path. `stakes: high`, `convene: true`.
- **D-06 (GenerateFolioAction reconciles instead of rebuilding):** Replace `items()->delete()` + re-insert with a reconcile by source key inside the existing lock/transaction: for each computed line `(source_type, source_id)` → `updateOrCreate` (touches `description`, `amount_usd` only); generated rows whose source is no longer billable (cancelled booking) are deleted **unless they carry a dispute** (then they are kept and a matching `adjustment` row is not auto-posted — the row is simply reconciled to `amount_usd` 0 with the original description; the dispute keeps its subject). Rows with `source_type` `manual`/`adjustment` are **never touched**. Totals via `Folio::recalculateTotals()` (D-07). Row ids/uuids become stable across refreshes; update `ExpressCheckoutTest` exactly-once tests to assert uuid stability across two refreshes (stronger than today). Existing guards (settled folio, checked-out reservation) unchanged. `stakes: high`, `convene: true`.
- **D-07 (totals):** `Folio::recalculateTotals(): void` = one `SELECT COALESCE(SUM(amount_usd),0)` over the folio's items, written to both `subtotal_usd` and `total_usd`; only ever called by an action that already holds the folio row lock (Generate, PostFolioItem). Never computed in PHP from a stale collection. Concurrency test (sqlite cannot contend): interleave `post → generate → post → credit → generate` from two staff users and assert `total_usd == SUM(items)` after every step, plus the second-of-two-settles and post-on-settled 422 guards; a unit test asserts the action opens a transaction and locks (`DB::shouldReceive('transaction')`/query-log `for update` on mysql grammar is optional). `stakes: medium`, `convene: false`.
- **D-08 (idempotency):** Header `Idempotency-Key` (string ≤64, merged into the request in `prepareForValidation` as `idempotency_key`). **Optional** on line items, **required** on payments (D-11). Stored on the row; unique per `(folio_id, key)` for items and per `(payable_type, payable_id, key)` for payments. Replay with the same key: if `kind/description/quantity/unit_price` (items) or `method/amount_usd` (payments) match → return the original row's folio, **200**, no write; if they differ → new `IdempotencyConflictException` (`idempotency_conflict`, **409**, context `{idempotency_key}`). Checked inside the lock so two racing replays cannot both insert (the unique index is the last line of defence; a `QueryException` on it is re-read and returned as replay). No TTL. Rationale: PITFALLS §2 demands retry safety; a header is the standard contract and keeps bodies clean. `stakes: high`, `convene: true`.

### FOLIO-03 — Disputes

- **D-09 (history table, not columns):** New table `folio_item_disputes`: `id`, `uuid`, `folio_item_id` FK cascadeOnDelete, `status` string (`FolioDisputeStatus { OPEN, RESOLVED, REJECTED }`), `reason` string(500), `guest_id` FK nullable nullOnDelete, `user_id` FK nullable nullOnDelete (exactly one of the two set; app-enforced), `resolved_by` FK users nullable nullOnDelete, `resolved_at` timestamp nullable, `resolution_note` string(1000) nullable, timestamps; indexes `(folio_item_id, status)`, `status`. Model `FolioItemDispute` (`HasUuid`, `LogsActivity`), `FolioItem::disputes()` hasMany + `latestDispute()` hasOne latestOfMany, `Folio::disputes()` hasManyThrough, `FolioItemDispute::scopeOpen()`. One open dispute per item enforced in the action under the folio lock, never by a partial index (MySQL has none). Rationale: skill rule "status + history over boolean flags"; re-disputes and staff decisions need a trail; the folio_items row stays a pure ledger line. Overrides the ARCHITECTURE.md "add columns" suggestion. `stakes: medium`, `convene: true`.
- **D-10 (guest route):** `PATCH /folio/items/{item}/dispute` in the existing `auth:guests + is_checked_in` group. Body `{ reason: required|string|max:500 }`. Ownership in `RaiseGuestDisputeRequest::authorize()` / service: `item.folio.reservation.guest_id === $request->user('guests')->id` else **404 `not_found`** (Phase 4 precedent: never confirm another guest's record exists; uuids are unguessable). Allowed on `open` and `settled` folios alike (flag only, no money effect). An open dispute already on the item → new `FolioItemDisputeOpenException` (`folio_item_dispute_open`, 422, context `{item_uuid, dispute_uuid}`); after `resolved`/`rejected` a new dispute may be raised (history). Responds 200 with `FolioItemResource` (item + `dispute`). `RaiseFolioDisputeAction::handle(FolioItem, Guest|User $raiser, string $reason)`: `DB::transaction`, lock the **folio** row (single lock, no reservation lock needed — no reservation write), check open, insert. `stakes: medium`, `convene: false`.
- **D-11 (staff route + permission):** `PATCH /cms/folios/{folio}/line-items/{item}/dispute` with `->scopeBindings()` (item outside the folio → 404 `not_found`), permission **`folios.dispute`** (new; seeded; granted to the same presets as `folios.post`). Body `{ action: required|in:raise,resolve,reject, reason: required_if:action,raise|string|max:500, note: required_if:action,resolve,reject|string|max:1000 }`. `raise` → `RaiseFolioDisputeAction` with the staff user; `resolve`/`reject` → `ResolveFolioDisputeAction::handle(FolioItem, User, FolioDisputeStatus $outcome, string $note)`: lock folio, require an open dispute else new `FolioDisputeStateException` (`folio_dispute_state`, 422, context `{item_uuid, status}`), stamp `resolved_by/resolved_at/resolution_note/status`. Resolution never moves money: a refund-worthy dispute is settled by posting a `credit` line (D-05) with `reverses_item_uuid` — the guide says so explicitly. Responds 200 with `FolioItemResource`. `stakes: medium`, `convene: false`.
- **D-12 (flags, never a gate):** `Folio::scopeWithOpenDisputes(Builder)` (`whereHas('items.disputes', status open)`), `Folio::openDisputesCount()` on loaded relations, `open_disputes_count` in `FolioResource` (D-02), and the reservation-level `folio {uuid,status,total_usd}` summary in `ReservationResource` gains `open_disputes_count` (check-out response only, still `whenLoaded`). `ReservationFilter` gains `has_open_disputes=1|0` next to `folio_status` (D-10 of Phase 3). `CheckOutReservationAction` is not touched; a test proves a settled folio with an open dispute checks out 200 and an open folio with a dispute is refused with `folio_unsettled` only. `stakes: low`, `convene: false`.

### FOLIO-04 — Payments

- **D-13 (endpoint, reuse, permission):** `POST /cms/folios/{folio}/payments`, permission **`folios.settle`** (taking money is what that permission already means; no new permission). `RecordFolioPaymentRequest` body `{ method: required|enum PaymentMethod (cash|on_arrival), amount_usd: required|numeric|min:0.01|max:99999.99, note: nullable|string|max:1000 }`, header `Idempotency-Key` **required** (D-08). `RecordFolioPaymentAction::handle(Folio, User $recorder, array $data, string $idempotencyKey)`: `DB::transaction`; lock folio; `settled` → `folio_settled` 422; replay check (D-08); `balance = balanceDueUsd()` from `ledgerPayments()` (D-03); `amount_usd > balance` → new `FolioOverpaymentException` (`folio_overpayment`, 422, context `{balance_due_usd, amount_usd}`) — overpayment/change-making is not modelled and a zero-balance folio therefore rejects any payment; call the existing `RecordCashPaymentAction::handle($folio, ...)` (payable = Folio; the reservation-status side effect in it is a no-op for folios) and set `payments.idempotency_key`; recompute balance; **auto-settle** when balance is `0.00` (`status = settled`, `settled_at = now()`), which is exactly what lets SC3 "paid to zero passes the check-out gate" hold with no second call. Respond **201** with the full `FolioResource` (payments included); replay → 200 same shape. `POST /cms/folios/{folio}/settle` stays as the "take the whole balance and close" shortcut, unchanged this phase (see Deferred). Migration: `payments.idempotency_key string(64) nullable` + unique `(payable_type, payable_id, idempotency_key)`. `stakes: high`, `convene: true`.
- **D-14 (lock order & auditing):** Every Phase 5 writer locks only the folio row (reservation → folio order is preserved for any caller that also locks the reservation, because none of the new actions lock the reservation at all). Activity: model `LogsActivity` on `FolioItem`, `Payment`, `FolioItemDispute` already records created/updated with the authenticated causer (staff user or guest); add explicit `activity()->log('folio.auto_settled')` with `{folio_uuid, paid_usd}` when D-13 auto-settles, so night audit can distinguish it from a manual settle. `stakes: low`, `convene: false`.

<objective>
Put housekeeping tasks into the merged operations queue as the third item type (HK-05; D-11b, D-12, D-13, D-14): one `OperationsQueueType` registry drives the queue's resolve, permissions, index, summary, status validation, mirror ids and item shape; the polymorphic assign/status actions gain a task arm that delegates to the housekeeping single writers; tasks mirror to Firestore through a queued listener. After this plan the dashboard's live operations queue shows and progresses housekeeping tasks next to service requests and tickets.

Purpose: ROADMAP criterion 2 ("The same tasks appear in the merged operations queue as the housekeeping-tasks type (rows carry room_number and allowed_statuses) and can be assigned and progressed via /operations/queue/housekeeping-tasks/{uuid}").
Output: the registry, the widened queue service, request, controller, resource, actions and mirror, the task mirror listener, advisory `allowedTargets()` on the request and ticket status enums, the `withRoomNumber()` scope, and the tests.
</objective>

## Flagged Assumptions

- **FA-6.05-1 (advisory allowed_statuses).** Requests and tickets have no enforced transition table, so their `allowed_statuses` lists every other value the queue accepts; only tasks (and bookings, plan 06-08) advertise an enforced table. Phase 7 may tighten tickets.
- **FA-6.05-2 (assign actor).** D-13 names `handle(item, User)` for assign; an optional trailing `?User $actor` is added so the pending → assigned history row records who assigned. Additive; existing callers are unaffected.
- **FA-6.05-3 (per-type cap).** Each type is capped at 500 open rows before the merge (3 × 500 total); a type beyond 500 open items is silently truncated in the queue, as documented in D-12 (SQL UNION deferred).
- **FA-6.05-4 (no-alias exception).** The dedicated `/housekeeping/tasks/{task}/assign|status` verbs and the queue verbs both write tasks; HK-05 requires the queue verbs, so this is a deliberate exception to the no-alias-routes rule (D-13), recorded in the summary.

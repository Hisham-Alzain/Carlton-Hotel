# Phase 9: Night Audit & Reports — decisions

Date: 2026-10-03. Mode: MVP. Consultant: Codex planning agent, under the owner's delegated autonomous engineering/QA/consultant workflow. These are implementation decisions based on the repository, not a claim of an external council vote. Read `09-RESEARCH.md`, `09-VALIDATION.md`, and the executable plans with this file.

## Scope and contract

AUDIT-01..03 and REPORT-01: persist a business-date closeout snapshot, acknowledge its checks and blockers with traceable staff actions, close a date in sequence, and provide exact bounded report aggregates. No source-domain operation occurs when acknowledging an audit: it never cleans rooms, pays folios, resolves tickets/disputes, checks guests out, or changes reservations. Those workflows keep their existing permissions and single writers. No exports, scheduled jobs, reopening dates, historical reconstruction, dashboard redesign, or automatic ledger posting.

All paths below are relative to `/api` (actual routing; older requirements incorrectly say `/api/v1`). All are `auth:users`:

| Endpoint | Permission | Input |
|---|---|---|
| GET `/operations/night-audit` | reports.view | optional strict `date=Y-m-d`; required for first initialization |
| PATCH `/operations/night-audit/checks/{check}` | reports.manage | `status: resolved|overridden`, required trimmed `note` <=1000 |
| PATCH `/operations/night-audit/blockers/{blocker}` | reports.manage | required trimmed `note` <=1000 |
| POST `/operations/night-audit/{audit}/close` | reports.manage | no client date, actor, status, or counts |
| GET `/reports/dashboard` | reports.view | `date_from`, `date_to`, both or neither; inclusive max 31 calendar days |

**D-01 — Persistent business date.** A singleton `night_audit_states` row stores `current_business_date` and nullable `last_closed_date`. The first explicit GET date initializes it; a request without a date before initialization fails 422 `night_audit_date_required`. After initialization omitted date uses persisted `current_business_date`, never the wall clock. An explicit date can read an existing audit (including closed history); creation is permitted only for the current business date. A different uncreated date fails 422 `night_audit_date_mismatch` with `current_business_date`. No default date in migrations/seeders. Date initialization is operational setup performed by the already authorized first reader, not a backfill from the oldest booking. Risk: an operator can deliberately choose a mistaken initial date; record this setup prerequisite in the guide. No reset endpoint in MVP.

**D-02 — Atomic initialization/open/close.** All three run in transactions. Initialize with unique singleton identity using Laravel's race-safe create-or-first/insert-or-ignore pattern, then reselect `lockForUpdate`; do not swallow arbitrary database errors. Unique `night_audits.business_date`; checks unique `(night_audit_id,type)`; blocker unique `night_audit_check_id`. Opening serializes on the singleton then the audit. Resolve actions lock audit before child; close locks singleton then audit and observes latest child states under that audit lock. Every audit mutation takes the audit lock, preventing close-vs-resolution races. SQLite tests assert lock intent but cannot prove concurrent MySQL row locking.

**D-03 — Snapshot, not reconstructed history.** Evaluate five categories once on first opening and persist `evaluated_at` UTC and an explicit `snapshot_basis = current_state_at_open`. Reopening never refreshes counts/evidence or duplicates children. Dirty rooms, tickets, disputes are current state when opened, even if the business date is old. Arrival/departure matching uses the chosen business date. The response and guide state this limitation. No global lock of all source domains; independently queried categories may see a source write during evaluation. This is an operational review snapshot, not a serializable accounting cut-off. Changes after opening must be checked in the source screens before staff attest/override. Closure freezes this attestation, not the rest of the hotel.

**D-04 — Exactly five checks and bounded evidence.** Enum types ordered `unsettled_departures`, `unassigned_arrivals`, `dirty_rooms`, `open_high_priority_tickets`, `open_folio_disputes`. Each has exact `issue_count`, up to 20 stable ordered public evidence UUIDs, `evidence_truncated`, localized label, status, note and actor/time. Category counts use COUNT/EXISTS and samples use LIMIT; no source `get()` of arbitrary size. JSON evidence is an immutable presentation snapshot and is never filtered by SQL. An empty category starts `passed`, without human actor/note; nonempty starts `pending` and creates exactly one category blocker. A blocker links its check and exposes its category/count/evidence through that relation. This bounds each audit to five checks and at most five blockers, regardless of property size. Evidence contains public UUIDs and minimal identifiers, no guest PII or complaint text.

**D-05 — Evaluation definitions.**

- Unsettled departures: reservations with `check_out = business_date`, status `confirmed|checked_in|checked_out`, and no folio or a folio with status `open`. Count reservations once; missing folios are issues, and even zero-balance open folios require settlement/acknowledgment. Pending/unverified/cancelled bookings excluded.
- Unassigned arrivals: reservations with `check_in = business_date`, status `confirmed|checked_in`, with no room lines or at least one `reservation_rooms.room_id IS NULL`. Count reservations once even with multiple unassigned lines. Checked-out/cancelled/unverified/pending bookings excluded.
- Dirty rooms: live, active rooms with status `dirty`; maintenance/inactive/soft-deleted rooms excluded.
- Open high-priority tickets: `TicketStatus::active()` and stored integer priority >=3 (the actual high-priority scale). Sample ticket UUIDs only.
- Open folio disputes: `folio_item_disputes.status = open`, independent of reservation date and folio status, because disputes remain relevant after checkout/settlement. Count dispute rows, not folios. This is a review flag, never a source checkout gate.

**D-06 — Attestations and readiness.** Check state is `passed|pending|resolved|overridden`. Only pending checks can transition to resolved or overridden; note is mandatory for both. Resolution attests staff verified the source; override explicitly accepts an exception. Neither re-evaluates/edits source data. Blocker `open -> resolved` separately requires a note. Updating the check never silently resolves its blocker, and resolving its blocker never marks its check complete. Response `readiness` has `checks_pending`, `blockers_open`, `can_close`; `can_close` requires zero of both and audit not closed. This deliberate two-part sign-off is explicit in guide and tests. Attempts on terminal children fail 422 `night_audit_item_resolved`; any mutation of a closed audit fails 422 `night_audit_closed`, checked first. Persist real authenticated actor FK and UTC acted-at; ignore/reject client actor metadata.

**D-07 — Closing is an explicit scope completion.** The roadmap goal says close each business date and requires last-closed state, while its original endpoint list omits a close operation. Add POST close above; do not misuse a final checklist tick to advance state. Under locks require audit is current, all checks terminal and all blockers resolved. Otherwise 422 `night_audit_not_ready` or date-mismatch. Successful close sets status `closed`, `closed_by`, `closed_at`, updates state's `last_closed_date` to audit date and `current_business_date` to next calendar date. A repeat close returns existing result 200 without changing timestamps or advancing twice. No reopen. Date progression uses calendar arithmetic, never wall-clock comparison.

**D-08 — Audit schema.** Four additive tables: singleton state (internal bigint PK/unique singleton key, current/last date, timestamps); audits (id, uuid unique, business_date unique, status string open/closed, evaluated_at, closed_by nullable users FK restrictOnDelete, closed_at nullable, timestamps); checks (id, uuid unique, audit FK restrictOnDelete, type string, status string, issue_count unsigned, evidence JSON, evidence_truncated bool, note nullable, acted_by nullable users FK restrictOnDelete, acted_at nullable, timestamps, unique audit/type); blockers (id, uuid unique, audit FK restrictOnDelete, check FK unique restrictOnDelete, status string open/resolved, note nullable, acted_by nullable users FK restrictOnDelete, acted_at nullable, timestamps). Model relationships must ensure blocker audit matches parent check; it is populated only by the single opener. Index actor FKs and audit/status query columns. No soft deletes or delete endpoints. UUIDs public, IDs internal. Models use HasUuid/HasFactory and audit traits where applicable; notes should not be duplicated to activity logs. Snapshot columns are immutable after creation in action code.

**D-09 — Permissions.** Add `reports.manage`; reports.view alone never writes checks/blockers or closes. Existing lazy GET writes only immutable snapshot creation per AUDIT-01, not a managerial attestation. Current presets are reception, kitchen, housekeeping, concierge, events, content_editor, content_manager; none is a hotel management preset. Do not grant reports.manage to a content manager or receptionist based on name. Seed string for explicit per-account assignment; super-admin existing Gate bypass remains. Catalogue changes 29 -> 30 permissions, group count remains 12. Re-pin exact count tests and assert preexisting presets unchanged. Document both reports.view and reports.manage required for a practical managerial account; do not assume manage implies view.

**D-10 — Report period and time.** Reports accept paired strict real `date_from/date_to`, ordered, at most 31 inclusive days. With neither, report hotel-local today via `HotelClock::today()` (unlike audit state, this is an ordinary date-range dashboard). Convert full inclusive period to `[HotelClock::dayWindow(from)[0], HotelClock::dayWindow(to)[1])` UTC for created timestamps. Include period start/end, timezone, generated_at UTC and explicit basis metadata. Invalid/partial ranges return standard 422 validation_failed. Do not call SQL DATE(created_at), assume every local day is 24 hours, or use database/server timezone defaults.

**D-11 — Occupancy definition.** Report booked room-nights over the period using one reservation_rooms line per booked room for reservations in `confirmed|checked_in|checked_out`. Intersect each half-open stay `[check_in,check_out)` with `[from,to+1)`; cancelled, pending, pending_verification excluded. Count multi-room lines independently, including an unassigned room line (it consumes sold room-type inventory). The model has no no-show status; do not invent one. Denominator = current active/live room count * number of period dates. Maintenance rooms remain physical capacity, explicitly documented; unavailable-room history is unavailable. Zero denominator => rate 0, not NaN/division error. Do not clamp overbooking to 100%; rate is a ratio in 0..N. Historical results use present room inventory and current reservation state, not a reconstructed historical inventory ledger. Return occupied_room_nights, available_room_nights, active_rooms, occupancy_rate. Arrivals/departures count reservations once by scheduled check_in/check_out within inclusive dates with same eligible states; no room-line join multiplication.

**D-12 — Revenue and cash are different measures.** `revenue.basis = posted_folio_lines`; exact signed SUM of `folio_items.amount_usd` whose created_at falls in the hotel UTC period. Generated reservation lines are posted totals, not nightly accrual; unsettled generated rows can later reconcile/reprice. Never call GenerateFolioAction during reporting. Expose charges_usd (positive), credits_usd (negative), net_usd, with currency USD. Document this operational posting view is not audited accounting revenue and can change while source folios are editable. Separately `collections` sums completed payments within created_at period: stays_usd (Reservation or Folio payable types, each Payment row exactly once), event_deposits_usd (EventInquiry), other_usd, total_usd. Neither join payments to folio items nor count Reservation/Folio balances a second time. Resolve morph types through getMorphClass without altering morph maps. Failed/pending payments excluded. Existing refunds are not subtracted: expose `refunds_included=false`, never label collections net cash after refunds.

**D-13 — Exact bounded aggregates.** Use database aggregate counts/sums; no materializing full money ledgers, per-day queries, per-reservation loops, or response detail rows. On SQLite SUM(DECIMAL) is REAL: aggregate integer cents using per-row rounded conversion (`CAST(ROUND(amount_usd * 100) AS INTEGER)`) and convert integer-string cents to exact 2dp with bcmath, or equivalent proven exact helper. On MySQL DECIMAL SUM/typed integer cents is exact. Negative values, 0.10 repeated, large values and no rows need tests. Never cast money to PHP float. A driver-specific overlap expression can use SQLite julianday difference and MySQL DATEDIFF with conditional min/max; bind all dates, not raw user SQL. Portability to the supported SQLite/MySQL pair is a test requirement; any unsupported driver must be explicit. Target <=12 domain SELECTs for report regardless of data or period size, <=16 on first audit open, <=6 existing audit reads; exclude authentication/session/permission bookkeeping and activity inserts. Re-pin measured justified budgets rather than silently inflating them.

**D-14 — Open work.** `open_work.service_requests` counts ServiceRequestStatus::active and `open_work.tickets` counts TicketStatus::active at request time. These are current backlog, not fabricated past-end-of-period counts or limited to records created in the selected period. Expose `basis=current_state`, include `as_of=generated_at`, and explain this alongside snapshot limitations. Housekeeping backlog is optional only if no additional requirement/scope creep; not required here.

**D-15 — Client adaptation.** Backend owns canonical fields/UUIDs; no `/v1` aliases or mock numeric IDs. Existing dashboard audit is gated FOLIOS_VIEW, displays `done` and a richer mock shape, and reports use synthetic ADR/RevPAR/source charts. Backend guide must list mapping and explicit omissions; do not fabricate ADR, RevPAR, MTD/YTD, revenue-by-source or shift window from data that cannot support them. The existing UI needs a later adapter/integration; flipping API capability nodes means endpoint coverage, not claiming the React mocks were wired. Both scopes remain backend milestone work.

**D-16 — Shared integration and safety.** Root/integrator alone edits routes, five locale files, permission seeder/count tests, guide/Postman/tree, shared planning state. Audit and reports engineers have disjoint new files/migrations/tests. Preserve database.sqlite and backups, unrelated work and Phase8 changes. Migration rollback only on a scratch DB, full suite after integration, independent QA, then one phase commit without push.

## A. Item 3 — `preferred_locale` accepts five locales (LOCALE-01)

**D-01 — Validation source.** `UpdateGuestProfileRequest` validates `preferred_locale` with `Rule::in(TranslatableRules::locales())` — the one accessor `SetLocale`, `BaseFilter` and translatable rules already share. No literal list anywhere. `prepareForValidation` lower-cases and trims the value (`'FR'` → `fr`); `'fr-FR'` is **rejected** (422), not folded. Still `sometimes`, still non-nullable.

**D-02 — Column stays `string(2)`.** All five configured codes are 2 chars. A guard test asserts every `cms.locales` entry fits the `guests.preferred_locale` column (length ≤ 2), so adding `pt_BR` to `CMS_LOCALES` fails CI before it truncates data. Widening the column is deferred until a region tag is actually configured.

**D-03 — Seed on first sign-in.** `VerifyOtpAction`, when (and only when) it **creates** a guest, sets `preferred_locale = app()->getLocale()` (already negotiated by `SetLocale` from `cms.locales`, so always valid). Existing guests are never overwritten by a header. Reason: the mobile guide tells the app to mirror `preferred_locale` into its own locale on first login, so a French app signing up a new guest was flipped to English. Additive: an app sending `Accept-Language: en` (or none) sees no change.

**D-04 — Other locale surfaces.** `GuestResource`, `GuestProfileResource`, `GuestDirectoryResource` already pass the value through; `GuestFilter` `in`/`eq` already accept any string — no change. No server push text is localized per guest today (no consumer of `preferred_locale` in `app/`); per-guest push localization is deferred (Phase 10 LOY-10 will need it and must read `preferred_locale`).

## B. Item 2 — `DELETE /auth/guest/me` (GACC-01..03)

**D-05 — Semantics: anonymize, never hard-delete.** The guest row stays (its id anchors reservations, folios, payments, tickets, reviews, disputes, service bookings) and is scrubbed of PII. New columns on `guests` (additive): `account_status string(16) NOT NULL default 'active'` indexed (`GuestAccountStatus` enum: `active`, `deleted`) and `account_deleted_at timestamp nullable`. History = `activity_log` entry `guest.account_deleted`. Not `SoftDeletes`: soft-delete scopes would hide the row from every staff relation (`$reservation->guest` → null) and from accounting joins, which is exactly what must not happen.

**D-06 — Route and contract.**
`DELETE /api/auth/guest/me`, inside the existing `auth:guests` group, `throttle:5,1` (keys on the guest id inside the auth group). Controller `GuestAuthController::deleteAccount` (camelCase custom verb). Request `Auth/DeleteGuestAccountRequest`: `confirm` **required|accepted** (body `{"confirm": true}`) — guards against an accidental or replayed bare DELETE; Dio/http send DELETE bodies. Success: **200** envelope, `message = custom.auth.account_deleted`, `data = null`. No 403 path (no permission; a staff token is 401 on the guest guard).

**D-07 — Blocking rules (422 `guest_account_deletion_blocked`).** Checked under the guest-row lock, all reasons collected (not first-fail):
- `active_reservation` — any reservation matching `GuestEntitlement::constrainLive()` on `HotelClock::today()` (in house, arriving, upcoming).
- `open_folio` — any folio with status `open` on any of the guest's reservations (GUEST_EXPRESS / STAFF_FORCE check-outs leave folios open; staff must settle first).
- `upcoming_service_booking` — a service booking with status pending|confirmed and `scheduled_at >= now()`.
Context: `{reasons: [...], booking_codes: [...]}` (reasons in that fixed order; booking codes of the offending reservations, sorted, ≤ 10). The app tells the guest to contact the front desk. `pending_verification` reservations and stale past `pending/confirmed` ones (no-shows) do **not** block — they are not live and must not trap a guest forever.

**D-08 — What happens to each table** (one `DB::transaction`, guest row `lockForUpdate` first; automatic model logging suppressed with `activity()->withoutLogging()` so the scrub itself writes no old PII):

| Data | Action | Why |
|---|---|---|
| `guests` PII: name, first_name, last_name, phone, phone_country, phone_verified_at, email, email_verified_at, bed_type, pillow_type, floor_preference, preferences_other, preferences_updated_at | set NULL; `account_status=deleted`, `account_deleted_at=now()`. `uuid`, `preferred_locale`, timestamps kept | phone/email NULL frees the unique keys, so the person can register again as a new guest |
| `personal_access_tokens` | delete **all** the guest's tokens (StaffService::deactivate pattern) | every device signed out |
| `device_tokens` | delete all | no push to a deleted account |
| `guest_notifications` | delete all | personal inbox, no accounting value |
| `guest_notes` (staff internal) | delete all | erasure; may hold health/allergy detail |
| `otp_codes` where identifier ∈ {old phone, old email} | delete | raw identifier is PII |
| `reservations` of the guest | keep row, `guest_id`, `booking_code`, `last_name`; set `phone = NULL` | accounting identity on the booking; booking-link (which needs `guest_id IS NULL`) can never re-attach them to someone else |
| `folios`, `folio_items`, `payments`, `refunds`, `folio_item_disputes` | untouched | accounting ledger, legal retention |
| `service_bookings`, `service_requests`, `tickets` (+ actions, recoveries), `event_inquiries` | untouched (linked to the anonymized row) | operational/financial records; see deferred for inquiry contact fields |
| `reviews` | kept; author renders with null names | ratings integrity (`rating_avg`); text is the guest's published UGC |
| `guest_documents` (ID scans) | rows + files on reservations that reached `checked_out` are **kept** (guest-registration record); all others deleted, files removed **after commit** | legal guest register vs. minimization; retention period is an owner action |
| `conversations` | status → `closed` | thread ends |
| `messages` sent by the guest | `body = NULL`, `attachment_path = NULL` (files removed after commit); Firestore `chats/{uuid}` re-mirrored after commit with `body: null, attachment_url: null, redacted: true`. Staff messages kept | erasure of guest-authored free text while staff side keeps the thread shape |
| `activity_log` rows whose subject is this guest | keep rows; remove keys name, first_name, last_name, phone, phone_country, email, bed_type, floor_preference, preferences_updated_at from `properties.attributes` and `properties.old` (PHP JSON rewrite, chunked) | audit trail of *what happened* survives, PII does not |
| new `activity_log` entry | `log_name default`, event/description `guest.account_deleted`, subject + causer = the guest, properties `{retained: {reservations, documents}}` counts only | staff-visible history (Phase 4 directory/profile, activity log) |

File deletion and Firestore re-mirroring run in `DB::afterCommit` callbacks; a failure there is logged (existing trait/`FileTrait` behaviour), never rolls back the erasure, and leaves at worst an orphan file — recorded risk R-4.

**D-09 — Idempotency and concurrency.** The guest row is locked first; if `account_status` is already `deleted`, the action returns the same 200 without writing or logging again (two racing requests on the same token → one erasure). A second call after success is **401** (tokens are gone) — documented as expected. No `Idempotency-Key` (not a payment-like write).

**D-10 — Re-registration.** Signing in again with the same phone/email creates a **new** guest (old row has NULL identifiers). Old stays are not visible to the new account and cannot be re-linked. Documented in the mobile guide and the in-app confirmation copy (Flutter action).

**D-11 — Layers.** `Actions/Guest/DeleteGuestAccountAction::handle(Guest $guest): array` (constructor-injected deps; private methods per table group, each ≤ ~40 lines); `AuthGuestService::deleteAccount()` delegates (service pattern of the file). Exceptions (flat in `app/Exceptions/`): `GuestAccountDeletionBlockedException` (`guest_account_deletion_blocked`, 422) and `GuestAccountDeletedException` (`guest_account_deleted`, 422, D-12). Keys in all 5 locales.

**D-12 — Staff-side visibility (Phase 4 surfaces).**
- `GuestDirectoryResource` and `GuestProfileResource` gain `account_status` and `account_deleted_at` (additive).
- `GET /api/guests` (Phase 4 block, `routes/api.php:637-647`, `guests.view`) **excludes** deleted accounts by default (a page of blank rows is useless); `?account_status=deleted` (or `in`) shows them. `GuestFilter` whitelists `account_status` eq/in; the default exclusion lives in `GuestService::index` when the param is absent.
- `GET /api/guests/{guest}` still works for a deleted guest (reservations link to it) and shows the flag.
- Staff writes that would re-attach personal data — `POST /api/guests/{guest}/notes` and `PATCH /api/guests/{guest}/preferences` (`guests.edit`) — on a deleted account → 422 `guest_account_deleted`.
- `receipt.blade.php` falls back to `$reservation->last_name` when the guest names are null, so a reprinted receipt still names the payer.

**D-13 — App-store requirements.** Apple 5.1.1(v): in-app initiation of deletion — met by this route. Google Play account-deletion policy: also a **web** path to request deletion — met with zero extra backend because the website already has guest OTP sign-in (`API_GUIDE_WEBSITE.md`) and can call the same route (owner/website action). Partial retention (bookings/payments/registration documents) is allowed by both stores when disclosed — privacy policy update is an owner action.

## C. Item 4 — Exchange rates (FX-01..02)

**D-14 — Where rates live: an append-only table, not config, not `site_settings`.**
- `config/currency.php` (deploy-time, not data): `base => 'USD'` (fixed, matches DECIMAL USD money), `currencies => ['SYP' => ['display_decimals' => 0], 'TRY' => ['display_decimals' => 2]]`, `stale_after_hours => (int) env('CURRENCY_STALE_AFTER_HOURS', 168)`. A `App\Support\CurrencyConfig` accessor fails closed (non-ISO code, USD listed as quote, empty set → `RuntimeException`), the `TranslatableRules` pattern.
- `exchange_rates` table: id; `uuid` unique; `currency char(3)`; `rate DECIMAL(20,6)` = **units of `currency` per 1 USD**; `note string(255) nullable` (source, e.g. "CBS bulletin"); `set_by` FK users `restrictOnDelete` indexed (users are deactivated, never deleted); timestamps. Index `(currency, id)` (latest-per-currency lookup; leftmost prefix also serves `currency` filters). No soft deletes, no update, no delete route: **each change is a new row** (history = the table; money-adjacent ⇒ immutable). `LogsActivity` on the model (create only) for the staff activity feed.
- Rejected: config/env rates (a deploy per rate change; nobody at the hotel can deploy); `site_settings` (edited under `cms.edit` by content editors, JSON value not DECIMAL, no history — wrong blast radius); external FX API (SYP has no reliable market feed; the hotel's own board rate is the business truth) — deferred.

**D-15 — Endpoints.**

| # | Method + path | Guard / middleware | Body / query |
|---|---|---|---|
| 1 | GET `/api/public/exchange-rates` | none (public), `throttle:60,1` | none |
| 2 | GET `/api/cms/exchange-rates` | `auth:users`, `permission:pricing.edit` | none |
| 3 | POST `/api/cms/exchange-rates` | `auth:users`, `permission:pricing.edit` | `currency` (configured, upper-cased in `prepareForValidation`, never USD), `rate` (string/number matching `^\d{1,14}(\.\d{1,6})?$`, > 0), `note` nullable ≤ 255, `confirm_large_change` boolean optional |
| 4 | GET `/api/cms/exchange-rates/history` | `auth:users`, `permission:pricing.edit` | `currency` eq/in filter, `per_page` (BaseService ceiling) |

Route 1 is registered in the public block; it is public (not guest-auth) because prices are shown before sign-in and the website needs the same numbers.

**D-16 — Response shapes.** Routes 1 and 2 (not paginated — bounded by config, the `/public/settings` precedent):
```
data: { base: "USD", stale_after_hours: 168,
        rates: [ { currency: "SYP", rate: "13000.000000"|null, display_decimals: 0,
                   updated_at: "2026-10-04T08:00:00Z"|null, is_stale: true|false } ] }
```
One entry per configured currency in config order; a currency with no row yet returns `rate: null, updated_at: null, is_stale: true` (the app keeps its built-in fallback). `rate` is a decimal **string** (no float drift). Route 2 entries add `note` and `set_by {uuid, name}|null`. Route 3 returns 201 with one history entry `{uuid, currency, rate, note, set_by, created_at}`; route 4 pages the same shape newest first (`id desc`). `is_stale = updated_at is null OR now - updated_at > stale_after_hours`. Conversion is **display-only on the client** (`usd × rate`, rounded to `display_decimals`); the server never charges, stores or settles in SYP/TRY.

**D-17 — Fat-finger guard.** If a current rate exists and the new rate differs by more than **50%** either way (bcmath, scale 6), the write needs `confirm_large_change: true`, else 422 `exchange_rate_large_change` with context `{currency, current_rate, proposed_rate, change_percent}`. This also catches a 100× SYP redenomination slip. `RecordExchangeRateAction` runs in a transaction and locks the currency's latest row (`lockForUpdate`) so two concurrent writers compare against the same baseline.

**D-18 — Caching.** No server cache (two bounded queries; Phase 10 precedent "no caching of rates"). Route 1 sends `Cache-Control: public, max-age=300` so app/CDN reuse it for 5 minutes; a new rate is visible within 5 minutes worst case. App guidance: fetch on launch and on the checkout screen, keep last good copy, show "rates as of …" when `is_stale`.

**D-19 — Permission: reuse `pricing.edit`. High stakes, explicit.** All staff rate routes are `permission:pricing.edit`; reads use it too (a pricing-only role has no view/edit split; one string).
- Blast radius: `pricing.edit` is in **no preset** and enforced nowhere today, so no seeded role silently gains anything (Phase 7 lesson: reusing `tickets.*` widened reception/concierge into guest chat; Phase 8 lesson: money writes get their own string — here the write is a display rate, not a ledger movement). Only accounts already granted `pricing.edit` per account gain access — owner action to audit them before deploy.
- Catalogue stays **30 / 13**; no seeder, preset, `SeederTest`, `PermissionsGroupedTest` or Phase 10 count change. `CmsAccessControlTest::$notYetBuilt` becomes `[]`. `SeederTest:123` role-less allowlist keeps `pricing.edit` (still per-account). `EscalationBlockedTest` keeps working (it grants, does not need inertness). `API_GUIDE_DASHBOARD.md:182` is rewritten.
- Dissent recorded: a dedicated `exchange_rates.manage` (31/14) would separate FX from future room-rate pricing. Rejected: it re-pins three tests and Phase 10's counts for no present access difference; if room-rate editing ever lands under `pricing.edit` and needs a different audience, split then (additive).
- Super admin passes via `Gate::before`.

**D-20 — Locales.** Every new key in all 5 files (en, ar, fr, tr, es), appended at the end of each section, never reordered: errors `guest_account_deletion_blocked`, `guest_account_deleted`, `exchange_rate_large_change`; `auth.account_deleted`; `messages.exchange_rate_recorded`; attributes `confirm`, `currency`, `rate`, `confirm_large_change`. 422 messages asserted in all 5 locales for each new error code.

## Risks and dissent

- **R-1 (legal retention).** Keeping `reservations.last_name`, checked-out ID scans and payments after "delete my account" is a legal-basis retention. Must be disclosed in the privacy policy; retention periods unconfirmed (owner).
- **R-2 (stolen token).** A stolen guest token can erase the account. `confirm` + throttle limit accidents, not theft. Fresh-OTP re-auth (`OtpPurpose::ACCOUNT_DELETION`) was considered and **deferred**: it changes the app flow the Flutter team asked for; revisit if abuse appears.
- **R-3 (audit rewrite).** Redacting `activity_log.properties` edits an audit trail. Chosen over leaving PII because the log is the largest PII copy; event rows, timestamps and causers survive.
- **R-4 (orphans).** After-commit file/Firestore cleanup can fail and leave orphan files or an unredacted Firestore doc; logged, not retried. A reconciliation command is deferred.
- **R-5 (blocked forever).** An open zero-balance folio blocks deletion until staff settle it. Accepted (accounting first); the 422 context tells the app which booking.
- **R-6 (stale FX).** If nobody updates rates, `is_stale` turns true after 7 days; nothing blocks. The hotel must own the update routine (owner action).
- **R-7 (SYP denomination).** Syria's pound redenomination means the hotel must enter rates in the unit the app displays; the 50% guard forces a confirm on a 100× change.
- **R-8 (ID scans on the public disk).** `SubmitDocumentsAction` stores ID scans on the `public` disk (pre-existing, Phase 4). Not fixed here; flagged for a security follow-up.
- Dissent kept: hard delete (rejected, D-05); SoftDeletes (rejected, D-05); new `exchange_rates.manage` (rejected, D-19); server-side rate cache (rejected, D-18); guest-auth rates route (rejected, D-15).

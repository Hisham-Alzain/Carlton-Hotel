<objective>
Close the Phase 10 verification gap (truth #7, LOY-23): when a guest deletes their account, forfeit the loyalty balance (expire entries through `LoyaltyLedger`) and close every unspent voucher inside the deletion transaction, idempotently and never negative, and record counts only in the deletion audit entry. Also re-forfeit when a reversal later runs for an already-deleted guest, so the balance cannot come back.

Purpose: ROADMAP Phase 10 "must add one thing: when a guest account is deleted (9.1 `DeleteGuestAccountAction`), the loyalty balance is forfeited (expire entries), and the deletion activity counts stay PII-free." Without it, `outstanding_points`/`liability_usd` are overstated and an erased account keeps live points and vouchers.
Output: 1 new ledger method, 1 new action, 2 wired actions, 3 new test files, 1 updated test.
</objective>

## Phase Goal

ROADMAP Phase 10 goal (verbatim): "Guests earn integer points once per settled folio, see a FIFO-expiring balance and ledger, redeem catalog rewards into vouchers and pay part of a booking with points; cancellations undo every loyalty effect without ever producing a negative balance. Staff configure the six program values, manage the catalog, adjust points with an audited reason and report issued/redeemed/expired points." This gap plan delivers the ROADMAP "depends on" obligation for 9.1 account deletion. Plan 10-17 adds the guards (warning job, staff adjust, report filter) and the docs.

## Standing rules

Same as 10-01 (rules 1-15, M-1..M-10). In addition, for this gap:

- G-1. `LoyaltyLedger` is the only class that changes `points_remaining` or writes `loyalty_ledger_entries`. The deletion and the new action never update batches directly.
- G-2. Lock order is reservation -> folio -> guest -> batches -> vouchers. The deletion takes no reservation or folio lock, so for it the order is guest -> batches -> vouchers. Batch and voucher rows are only locked while the guest row lock is held.
- G-3. No migration, no route, no lang key, no new `error_code`, no new enum case. Voucher closing uses the existing `LoyaltyVoucherStatus` cases `void` and `expired`; the ledger uses the existing `expire` entry type (Q16 contract strings unchanged).

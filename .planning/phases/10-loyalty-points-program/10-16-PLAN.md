Also re-forfeit when a reversal later runs for an already-deleted guest, and earn nothing when a folio of a deleted guest is settled later, so the balance cannot come back.

- G-1. `LoyaltyLedger` is the only class that changes `points_remaining` or writes `loyalty_ledger_entries`. The deletion and the new action never update batches directly.

## Flagged Assumptions

- **FA-10.16-1 (probe: adjacency, LOY-23, unresolved).** "When two things are exactly equal or just touch?" Planner interpretation: a batch at or past expires_at but unswept is forfeited by the deletion (same `expire:batch:{id}` key, the sweep later writes nothing); a voucher at exactly expires_at is closed as `expired`, one still valid as `void`. Tested in Tasks 1-2. Consultant may overrule.
- **FA-10.16-2 (probe: empty, LOY-23, unresolved).** "Empty, single-element or null input?" Planner interpretation: no batches, no vouchers, an active batch with 0 left, or no settings row all give counts 0 and write nothing; deletion is never blocked by loyalty state. A single batch is the general path. Tested in Tasks 1-2.
- **FA-10.16-3 (probe: ordering, LOY-23, unresolved).** "When elements compare equal, is output order specified and stable?" Planner interpretation: batches by `expires_at, id` (Q14), vouchers by id; equal expiries are broken by id. Tested in Task 1.
- **FA-10.16-4.** Forfeited points are recorded with the existing `expire` type (ROADMAP: "forfeited (expire entries)"), so the report's `expired_points` includes forfeits and the staff ledger shows them as expiry; the deletion audit entry carries the forfeit counts. No `reason` text is written on these entries (it would need a stored translation).
- **FA-10.16-5.** The re-forfeit in `ReverseLoyaltyForReservationAction` closes the cancellation path: a stale (past check_out) pending or confirmed booking, which 9.1 D-07 does not count as live, can be cancelled by staff after the deletion. Tests reach that state only through `POST /api/reservations`, `travelTo` and `DELETE /api/auth/guest/me` (G-7, review item 2), and cover both refund outcomes (review item 5). It touches LOY-17 code only for deleted guests; existing reversal behaviour and return shape are unchanged.
- **FA-10.16-6 (review item 4, decided: manual MySQL verification; reservations-first rejected).** 9.1 deletion locks the guest and then writes the guest's reservations (phone null-out); a staff cancel locks the reservation, then the folio, then the guest. A cancel and a deletion for the same guest can therefore deadlock on MySQL and one of them answers 500. Locking the guest's reservations before the guest in the deletion was considered and rejected: (a) it contradicts 9.1 D-09 ("the guest row is locked first"), pinned by `DeleteGuestAccountActionTest::test_the_guest_row_is_locked_first`; (b) it is not consistent with every path: a points booking (`CreateReservationAction`) locks room_type, then the guest, then inserts the reservation, and a locking read of the guest's reservations taken before the guest lock also gap-locks that guest's `reservations.guest_id` range under InnoDB REPEATABLE READ, so the deletion would deadlock with a points booking instead; locking only by primary key avoids the gap lock but needs a plain read first, which under REPEATABLE READ fixes the snapshot before the guest lock and could let `assertDeletable` miss a booking committed in between. Accepted because both sides are single transactions: the deadlock victim rolls back completely (no partial erasure, no half reversal) and a retry succeeds with the same end state. Recorded as a Manual-Only Verification row in 10-VALIDATION.md (Task 3 item 4). The forfeit's own locks stay before the reservations write.
- **FA-10.16-7 (review item 1, decided: add the skip).** A settlement after deletion is reachable, so no test can be cited to the contrary: 9.1 lets a guest with a stale confirmed no-show delete (`GuestAccountDeletionGuardTest::test_stale_confirmed_no_show_does_not_block`), `GenerateFolioAction` opens a folio for any reservation, and `SettleFolioAction` / `RecordFolioPaymentAction` call `EarnLoyaltyPointsAction`. A second path is a pending_verification booking (not live, D-07) that staff later confirm, check in and settle. The skip logs `loyalty.earn_skipped_deleted` with `skipped_points` only, even when that is 0, so every skipped settlement is visible.
- **FA-10.16-8 (review item 11, decided: 200 with redacted data).** Following 9.1 D-12 (staff reads of a deleted guest keep working because reservations and ledger rows link to it), `GET /api/cms/loyalty/guests/{guest_uuid}` and its ledger answer 200 for a deleted guest, not 404. The data is already redacted by the 9.1 scrub (`guest.name` null) and shows `available_points` 0 plus the forfeit `expire` rows. No `account_status` field is added to the loyalty view (additive but not needed): the dashboard reads it from `GET /api/guests/{guest_uuid}`, which carries it since 9.1. Plan 10-17 documents this.
- **FA-10.16-9 (review item 3 evidence).** 9.1 D-10 says signing in again creates a new guest; the Task 1 sign-in-again test adds that the new account starts with 0 available and 0 lifetime points. Plan 10-17 quotes the behaviour in the mobile guide only after this test passes.
